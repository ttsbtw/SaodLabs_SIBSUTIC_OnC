# Лабораторная работа № 1
## Сбалансированные деревья поиска. Красно-чёрное дерево

### 1. Цель работы

Реализовать красно-чёрное дерево поиска на языке Си и исследовать время поиска заданного и максимального ключа в сравнении с обычным бинарным деревом поиска.
### 2. Структура данных и интерфейс

Узел RBT содержит ключ `uint32_t`, строковое значение, цвет, указатели на левого и правого ребёнка и родителя. `NULL` обозначает чёрный внешний лист. Пустое дерево имеет корень `NULL`.

Реализованы `rbtree_add`, `rbtree_lookup`, `rbtree_delete`, `rbtree_min`, `rbtree_max`, `rbtree_free`, `rbtree_print_dfs`. Ключи всех функций имеют тип `uint32_t`, согласно требованию экспериментальной части. При повторном ключе обновляется значение; узлы с одинаковыми ключами не создаются. Строки копируются и освобождаются библиотекой.

Вставка выполняет обычный поиск места, создаёт красный узел, затем восстанавливает свойства перекрашиванием и поворотами. Удаление сначала находит узел и сводит исключение узла к случаю с не более чем одним ребёнком. Для узла с двумя детьми на его место переносится минимум правого поддерева. Если из исходной позиции удалён чёрный узел, выполняется восстановление чёрной высоты. Для `NULL`-ребёнка родитель передаётся отдельно.

BST реализовано независимо, без балансировки. Его поиск, вставка и освобождение итеративные, поэтому цепочка из 200000 узлов не переполняет стек.

### 3. Методика эксперимента

Размеры деревьев: 20000, 40000, …, 200000 узлов. Используются две последовательности:

1. Для среднего случая — псевдослучайная выборка без повторений из диапазона [10000, 1000000]. Частичное перемешивание Фишера–Йетса с xorshift32, начальное состояние 20260907. Остаток от деления при выборе индекса даёт небольшое смещение распределения, несущественное для данного учебного сравнения. Отсутствие повторов гарантирует точное число узлов.
2. Для худшего случая BST — возрастающие ключи 10000, 10001, …, 209999. Эта последовательность не обязана давать наиболее медленное из всех возможных RBT.

В каждом сценарии обе структуры получают одинаковые ключи в одинаковом порядке. Деревья постепенно наращиваются; в контрольной точке `lookup` ищет последний вставленный ключ. `max` ищет максимальный ключ от корня.

Для возрастающей последовательности BST подготавливается добавлением следующего узла справа от известного максимума. Структура и порядок узлов точно совпадают с результатом последовательных обычных вставок. Это сокращает только подготовку с O(n²) до O(n). Время подготовки, выделения памяти, вставки и печати не включается в таблицы. Поиск не использует сохранённый максимум: оба измеряемых алгоритма начинают с корня.


Это измерения повторного поиска одного ключа при прогретом кэше, включая небольшой расход на цикл и сохранение результата. Одна случайная последовательность не оценивает математическое ожидание по всем деревьям; название «средний случай» обозначает случайный порядок вставки, как в задании. Малые различия в наносекундах нельзя считать доказательством превосходства одной реализации. Различие размеров узлов BST и RBT также влияет на константы времени. Представленные цифры — измеренные значения конкретного запуска, а не универсальные нормативы. Дополнительные знаки в таблицах нужны для сохранения вывода, а не обозначают такую же точность измерителя.

### 5. Анализ результатов

При возрастающей вставке обычное BST превращается в правую цепочку. Последний добавленный ключ одновременно является максимумом: обе операции проходят все n узлов и требуют Θ(n) времени. При увеличении n с 20000 до 200000 время `bstree_lookup` выросло с 38.55 до 222.57 мкс (5.77 раза), а `bstree_max` — с 20.98 до 146.86 мкс (7.00 раза). Это согласуется с линейным ростом с учётом кэша и шума.

В RBT для той же последовательности поиск последнего ключа при 20000 и 200000 узлах занял соответственно 37.01 и 54.43 нс, а поиск максимума — 9.21 и 11.35 нс. Рост существенно слабее, чем у BST, что согласуется с логарифмической высотой. Поиск максимума быстрее поиска по ключу, потому что только следует по правым ссылкам и не сравнивает ключи на каждом шаге.

Для случайной последовательности время поиска колеблется: последний вставленный элемент каждый раз другой, и глубины этих элементов различаются. Время максимума BST местами меньше времени RBT: конкретная правая ветвь случайного BST может быть короткой, а узлы имеют разные размеры. Балансировка даёт гарантию высоты, но не гарантирует, что каждая отдельная операция будет быстрее.

Эксперимент согласуется с ожидаемым O(log n) для случайного BST, гарантированным O(log n) для RBT и Θ(n) для поиска конца вырожденного BST. Сам по себе конечный набор замеров не доказывает асимптотику; доказательство следует из высоты и числа посещённых узлов.

### 6. Ответы на контрольные вопросы

**1. Что такое сбалансированное дерево поиска? Какие виды известны?**

Это дерево поиска, в котором ограничения на форму поддерживают высоту O(log n). Примеры: AVL-дерево, красно-чёрное дерево, 2–3-дерево, B-дерево. У декартова дерева со случайными приоритетами высота логарифмическая в среднем; у splay-дерева отдельная операция может быть линейной, а логарифмической является амортизированная оценка операций.

**2. Структура узла красно-чёрного дерева.**

Ключ, значение, цвет RED/BLACK, ссылки на двух детей и родителя. В этой реализации ключ — `uint32_t`, значение — собственная копия строки. Отсутствующие дети представлены `NULL` и считаются чёрными.

**3. Принцип работы и свойства.**

Действует порядок BST: ключи левого поддерева меньше ключа узла, правого — больше. Каждый узел красный либо чёрный, корень чёрный, внешние NIL-листья чёрные, у красного узла оба ребёнка чёрные. Все пути от данного узла до внешних листьев имеют одинаковое число чёрных узлов. После изменения дерева алгоритм восстанавливает свойства перекрашиванием и поворотами, которые сохраняют порядок ключей.

1. Каждый узел дерева является либо красным (red), либо черным (black)
2. Корень дерева является черным узлом
3. Каждый лист дерева (NULL) является черным узлом
4. У красного узла оба дочерних узла – черные
5. У любого узла все пути от него до листьев, являющихся его потомками,
содержат одинаковое количество черных узлов

**4, 7 и 9. Вычислительная сложность и сравнение с BST.**

| Операция | RBT, худший случай | BST, ожидаемо при случайном порядке | BST, худший случай |
|---|---|---|---|
| Поиск ключа | O(log n) | O(log n) | O(n) |
| Вставка | O(log n) | O(log n) | O(n) |
| Удаление | O(log n) | O(log n) | O(n) |
| Минимум/максимум от корня | O(log n) | O(log n) | O(n) |
| Обход / освобождение узлов | Θ(n) | Θ(n) | Θ(n) |

Оценка удаления BST здесь теоретическая: для эксперимента требуются только вставка, поиск и максимум. Поворот занимает O(1). Балансировка после вставки использует не более двух поворотов, после удаления — не более трёх; перекрашивание может проходить вверх O(log n) уровней. Вставка дополнительно копирует строку длины L, поэтому её полное время в данной библиотеке O(log n + L). Память структуры — O(n) плюс хранимые строки. Рекурсивное освобождение RBT использует O(log n) стека, итеративное освобождение BST — O(1) дополнительной памяти.

Обход посещает n узлов, однако `rbtree_print_dfs` ещё выводит отступы и строки: фактическая стоимость — O(n + Σ глубин + суммарная длина строк), для RBT O(n log n + суммарная длина строк). Нельзя приравнивать стоимость форматированного вывода к стоимости одного посещения каждого узла.

**5. Алгоритм добавления с примером.**

Новый узел вставляется по правилам BST и окрашивается красным, поэтому число чёрных узлов на путях не меняется. Если родитель чёрный, исправление не требуется. Если родитель красный, рассматривается дядя — второй ребёнок дедушки:

- Красный дядя: родитель и дядя становятся чёрными, дедушка красным; проверка продолжается от дедушки.
- Чёрный дядя и «треугольник»: поворот вокруг родителя превращает конфигурацию в «линию».
- Чёрный дядя и «линия»: родитель становится чёрным, дедушка красным; поворот вокруг дедушки устраняет конфликт.

Левые и правые случаи симметричны. В конце корень окрашивается чёрным.

Пример: после вставки 10 и 20 имеем чёрный корень 10 с красным правым ребёнком 20. Вставка 30 создаёт два красных узла подряд. Дядя — чёрный NIL, конфигурация правая «линия». Левый поворот вокруг 10 и перекрашивание дают чёрный корень 20 с красными детьми 10 и 30. Вставка 15 вызывает случай красного дяди: 10 и 30 становятся чёрными, корень 20 в конце также чёрный.

**6. Алгоритм удаления с примером.**

Удаляемый узел без двух детей заменяется своим единственным ребёнком либо NIL. При двух детях его место занимает следующий по порядку узел — минимум правого поддерева. Для решения о балансировке важен исходный цвет узла, извлечённого из прежней позиции, а не только цвет найденного ключа.

Если извлечён красный узел, чёрная высота сохраняется. Если чёрный узел заменён красным ребёнком, ребёнок становится чёрным. Иначе образуется дефицит одного чёрного узла на путях через замену. Для брата w рассматриваются четыре случая:

1. Брат красный: перекрасить брата и родителя, выполнить поворот вокруг родителя; получить чёрного брата.
2. Брат чёрный, оба его ребёнка чёрные: сделать брата красным и перенести дефицит к родителю.
3. Брат чёрный, ближний ребёнок красный, дальний чёрный: перекрасить и повернуть брата, получив случай 4.
4. Брат чёрный, дальний ребёнок красный: передать брату цвет родителя, сделать родителя и дальнего ребёнка чёрными, повернуть родителя. Дефицит устранён.

«Ближний» и «дальний» определяются относительно стороны узла с дефицитом. Для другой стороны все повороты зеркальны.

Пример из `demo`: после вставок 10, 20, 30, 15, 25, 5, 1 и удалений 1, 20, 10 дерево имеет чёрный корень 25, чёрного левого ребёнка 15 с красным левым ребёнком 5 и чёрного правого ребёнка 30. Удаление чёрного листа 30 создаёт дефицит справа. Его брат 15 чёрный, дальний ребёнок 5 красный — зеркальный случай 4. После правого поворота вокруг 25 получается чёрный корень 15 с чёрными детьми 5 и 25. Полный вывод всех шагов сохранён в `demo_output.txt`.

**8. Доказательство оценки высоты.**

Обозначим через bh(x) число чёрных узлов на любом пути от x, не включая x, до NIL, включая NIL. Поддерево с корнем x содержит не менее 2^bh(x) − 1 внутренних узлов.

Доказательство по индукции: для NIL значение bh равно 0, внутренних узлов 0. У каждого ребёнка чёрная высота не меньше bh(x) − 1. По индукционному предположению оба поддерева вместе с x содержат не меньше `1 + 2·(2^(bh(x)−1)−1) = 2^bh(x)−1` внутренних узлов.

Пусть h — длина наибольшего пути от корня до NIL в рёбрах. Два красных узла не стоят подряд, а последний NIL чёрный, поэтому на этом пути среди узлов после корня хотя бы h/2 чёрных: bh(root) ≥ h/2. Следовательно, `n ≥ 2^bh(root)−1 ≥ 2^(h/2)−1`, откуда **h ≤ 2 log₂(n+1)**. Если высоту считать до последнего внутреннего узла, она на одно ребро меньше и тем более удовлетворяет той же верхней границе.

### 7. Разбор rbtree.c для защиты

#### 7.1. Как читать структуру и обозначения

`root` — указатель на корень всего дерева, а `left`, `right`, `parent` — связи между узлами. У корня `parent == NULL`. Пустое дерево и отсутствующие дети обозначаются `NULL`; отдельные объекты для чёрных NIL-листьев не выделяются.

В коде короткие имена имеют следующий смысл:

| Имя | Смысл |
|---|---|
| `x` | Текущий узел при вставке; при удалении — ребёнок, занявший освобождённую позицию |
| `p` | Родитель текущего узла |
| `g` | Дедушка при исправлении вставки |
| `u` в `rbtree_add` | Дядя: второй ребёнок дедушки |
| `z` | Узел с ключом, который нужно удалить |
| `y` в `rbtree_delete` | Сначала z; при двух детях — следующий по порядку узел |
| `xp` | Родитель x после перестановки связей, нужен даже при x == NULL |
| `w` | Брат узла x при исправлении удаления |
| `removed` | Исходный цвет узла, извлекаемого из своей позиции |

`p->key` означает обращение к полю структуры через указатель. `struct rbtree *` — указатель на узел, `struct rbtree **` — указатель на переменную, в которой хранится указатель на корень.

#### 7.2. rbtree_lookup — поиск ключа

**Принимает:** корень и ключ. **Возвращает:** адрес найденного узла либо `NULL`.

Цикл работает, пока узел существует и его ключ не совпадает с искомым. Если искомый ключ меньше текущего, переходим влево, иначе вправо. Такое исключение половины направлений возможно благодаря порядку BST. Цвета здесь не используются: они нужны для поддержания небольшой высоты, а сам поиск обычный.

```c
while (root && root->key != key)
    root = key < root->key ? root->left : root->right;
```

Оператор `&&` вычисляется слева направо с коротким замыканием: при `root == NULL` выражение `root->key` не вычисляется. Перемещение локальной переменной `root` не меняет корень у вызывающей функции — указатель передан по значению. Время O(h), для RBT O(log n), дополнительная память O(1).

#### 7.3. rbtree_min и rbtree_max — крайние ключи

**Принимают:** корень дерева или поддерева. **Возвращают:** адрес узла с минимальным или максимальным ключом; для пустого дерева — `NULL`.

Минимум находится переходами влево до отсутствующего левого ребёнка, максимум — аналогично вправо. В частности, `rbtree_min(z->right)` находит следующий после z ключ, если правое поддерево непустое. Время O(h), дополнительная память O(1).

#### 7.4. copy_value, color, paint — вспомогательные функции

- `copy_value(s)` выделяет память и копирует строку вместе с завершающим нулём: поэтому размер равен `strlen(s) + 1`. При `s == NULL` копируется пустая строка. Если `malloc` не смог выделить память, программа сообщает об ошибке и завершается. Возвращаемую строку позднее нужно освободить.
- `color(p)` возвращает цвет существующего узла, а для `NULL` возвращает `RB_BLACK`. Так реализовано правило «внешние листья чёрные» без отдельных NIL-объектов.
- `paint(p, c)` меняет цвет только существующего узла. Для `NULL` ничего не делает: отсутствующий лист всегда считается чёрным.

Эти функции объявлены `static`: их имена доступны только внутри данного файла C. Это не означает, что их локальные переменные сохраняются между вызовами.

#### 7.5. rotate_left и rotate_right — повороты

**Принимают:** адрес переменной корня и узел, вокруг которого выполняется поворот. Ничего не возвращают, меняют связи на месте. Левый поворот требует существующего правого ребёнка, правый — левого.

Левый поворот вокруг x выглядит так:

```text
        x                    y
       / \                  / \
      A   y       →        x   C
         / \              / \
        B   C            A   B
```

A, B, C — целые поддеревья, которые могут быть пустыми. Порядок ключей `A < x < B < y < C` сохраняется. Поворот не выделяет и не освобождает память, не копирует ключи и сам не меняет цвета.

Последовательность действий в `rotate_left`:

1. Сохранить правого ребёнка x в y.
2. Перенести левое поддерево y на место правого поддерева x; исправить его `parent`, если оно есть.
3. Связать y с бывшим родителем x. Если x был корнем, записать y в `*root`.
4. Сделать x левым ребёнком y и записать `x->parent = y`.

`rotate_right` выполняет зеркальные действия. Поворот имеет сложность O(1), потому что меняет фиксированное число ссылок независимо от размера поддеревьев.

**Зачем двойной указатель?** Если повернуть корень, нужно изменить саму переменную корня внутри вызывающей функции. Вызов `rotate_left(&root, x)` передаёт её адрес, а запись `*root = y` меняет её значение.

#### 7.6. rbtree_add — вставка и обновление

**Принимает:** корень, ключ и строку. **Возвращает:** актуальный корень после возможной балансировки.

Сначала выполняется обычный поиск позиции. `x` движется по дереву, `p` запоминает последнего посещённого узла — будущего родителя. Если ключ уже существует, функция копирует новое значение, освобождает старую строку и возвращает корень без балансировки: форма дерева не изменилась.

Почему новая строка копируется **до** освобождения старой? Аргумент `value` может указывать на ту же строку, которая уже хранится в узле. При обратном порядке копирование читало бы освобождённую память.

Если ключа нет, выделяется узел и выполняется инициализация:

```c
*x = (struct rbtree){key, copy_value(value), RB_RED, NULL, NULL, p};
```

Это составной литерал C: поля задаются в порядке объявления структуры — ключ, строка, цвет, левый ребёнок, правый ребёнок, родитель. `sizeof *x` при выделении памяти означает размер целого узла, а не размер указателя.

Новый узел красный, потому что это сохраняет количество чёрных узлов на старых путях. Возможный конфликт — красный родитель у красного ребёнка. Пока родитель красный, цикл исправляет этот конфликт:

- Красный дядя: перекрасить родителя и дядю в чёрный, дедушку в красный; `x = g` переносит проверку выше.
- Чёрный дядя, внутренний изгиб: сначала повернуть родителя, чтобы получить прямую конфигурацию.
- Чёрный дядя, прямая конфигурация: перекрасить родителя и дедушку, затем повернуть дедушку.

После цикла `root->color = RB_BLACK` обеспечивает чёрный корень, в том числе при первой вставке. У красного родителя в цикле обязательно есть дедушка: корень до исправления не мог быть красным родителем текущего узла без завершения переноса к корню.

Правильный вызов: `root = rbtree_add(root, key, value);`. Если не сохранить результат, после поворота можно оставить у себя указатель на прежний корень вместо нового. Структурная работа занимает O(log n), копирование строки длины L добавляет O(L).

#### 7.7. transplant — замена позиции узла

`transplant(&root, u, v)` устанавливает v на место u в связи с родителем u. Если u был корнем, новым корнем становится v. У существующего v обновляется поле `parent`.

Функция **не** освобождает u, не переносит автоматически его детей и не восстанавливает баланс. Эти действия выполняет `rbtree_delete`. Время O(1).

#### 7.8. rbtree_delete — удаление узла

**Принимает:** корень и ключ. **Возвращает:** новый корень, возможно `NULL`.

Сначала `rbtree_lookup` находит z. Если ключ отсутствует, дерево возвращается без изменений. Далее три случая:

1. Нет левого ребёнка: z заменяется правым ребёнком, который тоже может быть `NULL`.
2. Левый есть, правого нет: z заменяется левым ребёнком.
3. Оба ребёнка есть: `y = rbtree_min(z->right)` находит преемника. У y нет левого ребёнка, иначе y не был бы минимумом. Его правый ребёнок x занимает освобождаемую позицию, а сам y переносится на место z.

В третьем случае важно различать две ситуации. Если y — непосредственный правый ребёнок z, родителем x после удаления станет y, поэтому `xp = y`. Если y находится глубже, сначала `transplant(&root, y, x)` извлекает его из прежней позиции, а `xp` сохраняет прежнего родителя y. Затем y получает правое и левое поддеревья z, а их родительские ссылки исправляются.

Почему `y->color = z->color`, но для балансировки используется `removed`? На позиции z нужно сохранить его прежний цвет. Дефицит чёрной высоты возникает в прежней позиции y, поэтому имеет значение **исходный** цвет y, сохранённый до перекрашивания.

Освобождается именно z и его строка: y, если он был другим узлом, остаётся в дереве вместе со своим ключом и значением. После `free(z)` код больше не обращается к z. При удалении чёрного узла вызывается `delete_fix(&root, x, xp)`. Результат вызова снаружи нужно сохранять: `root = rbtree_delete(root, key);`. Время O(log n).

#### 7.9. delete_fix — восстановление после удаления

Функция получает корень по адресу, заменяющий узел x и его родителя p. Родитель передан отдельно, потому что x может быть `NULL` и выражение `x->parent` тогда недопустимо.

Условие `x != *root && color(x) == RB_BLACK` означает: исправлять дефицит, пока он не дошёл до корня и не может быть устранён перекрашиванием красного x. «Двойной чёрный» — способ объяснения дефицита; отдельного такого цвета в `enum` нет.

Если x слева, его брат `w = p->right`; ближний ребёнок брата — `w->left`, дальний — `w->right`.

| Состояние брата | Что делает код | Что происходит с дефицитом |
|---|---|---|
| w красный | Перекрашивает w и p, поворачивает p влево, заново находит w | Сводит к случаю чёрного брата |
| w чёрный, оба ребёнка чёрные | Красит w в красный; `x = p; p = x->parent` | Переносит дефицит на уровень выше |
| w чёрный, дальний ребёнок чёрный, ближний красный | Перекрашивает и поворачивает w вправо, заново находит w | Подготавливает последний случай |
| w чёрный, дальний ребёнок красный | Передаёт w цвет p, красит p и дальнего ребёнка в чёрный, поворачивает p влево | Устраняет дефицит; цикл завершается |

Если x справа, направления зеркальны. После поворота брат вычисляется заново, поскольку состав соседних узлов изменился. Запись `x = *root` в последнем случае заставляет условие следующей итерации стать ложным.

В конце `paint(x, RB_BLACK)` превращает красного заменяющего ребёнка в чёрного либо оставляет чёрный узел без изменений. Для пустого дерева это безопасный вызов с `NULL`.

Почему после проверок встречается `w->right` без отдельного `if (w)`? При `w == NULL` обе безопасные проверки цвета его детей возвращают чёрный, и исполнение попадает в ветку переноса дефицита. В следующую ветку, где происходит прямое обращение к полям w, такой указатель не попадёт.

#### 7.10. rbtree_free — освобождение памяти

Функция сначала освобождает левое и правое поддеревья, затем строку и сам узел. Это обход в глубину с обработкой родителя после детей. Если освободить узел раньше, читать из него указатели на детей уже нельзя.

При `root == NULL` функция сразу возвращается. После освобождения всего дерева переменная вызывающего кода сама не обнуляется: при дальнейшем использовании нужно написать `root = NULL`. Время Θ(n), стек рекурсии O(log n) для корректного RBT.

#### 7.11. rbtree_print_dfs — вывод дерева

Аргумент `level` задаёт текущую глубину; первый вызов делают с нулём. Функция рекурсивно выводит правое поддерево, затем текущий узел с отступом, затем левое поддерево. Поэтому дерево показано боком: большие ключи выше, меньшие ниже.

`PRIu32` из `<inttypes.h>` задаёт переносимый формат вывода `uint32_t`. Соседние строковые литералы в C объединяются, поэтому запись `"%" PRIu32` формирует подходящую строку формата. Тернарный оператор выбирает символ `R` для красного узла и `B` для чёрного. Печать не меняет дерево.

#### 7.12. Короткие ответы на вероятные вопросы

| Вопрос | Что ответить |
|---|---|
| Почему поиск не смотрит на цвет? | Цвет поддерживает высоту при изменениях, а направление поиска определяется только сравнением ключей. |
| Зачем у узла ссылка на родителя? | Для движения вверх при балансировке и восстановления связей при поворотах. |
| Зачем add и delete возвращают корень? | Вставка, удаление и повороты могут изменить корень. |
| Можно ли хранить отрицательные ключи? | Интерфейс использует uint32_t, поэтому отрицательные числа не входят в область ключей. |
| Кто владеет строкой value? | Дерево хранит собственную копию и освобождает её при обновлении, удалении или освобождении дерева. |
| Нужно ли освобождать результат lookup? | Нет, это адрес узла внутри дерева, а не новая копия. |
| Можно ли пользоваться узлом после его удаления? | Нет, его память уже освобождена. |
| Поворот меняет ключи местами? | Нет, он переставляет ссылки между существующими узлами и сохраняет порядок BST. |
| Почему удаление сложнее вставки? | При удалении чёрного узла может уменьшиться число чёрных узлов на части путей. |
| Что будет при удалении последнего узла? | Корень станет NULL, а восстановление безопасно завершится для пустого дерева. |

Для подготовки полезно вручную проследить три вставки 10, 20, 30 и удаление 30 из примера раздела о контрольных вопросах. На каждом шаге назвать текущие x, p, брата или дядю, объяснить выбранную ветку и показать, какие ссылки меняет поворот.

### 8. Вывод

Реализованы все требуемые функции красно-чёрного дерева, включая удаление с балансировкой. Эксперимент на 20000–200000 узлов показал линейное замедление обычного BST при возрастающих ключах и существенно более слабый рост времени RBT. Преимущество RBT — гарантированная логарифмическая высота при любом порядке вставки.
